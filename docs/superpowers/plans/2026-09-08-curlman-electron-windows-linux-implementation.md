# Curlman Electron Windows and Linux Implementation Plan

Date: 2026-09-08  
Design: `docs/superpowers/specs/2026-09-08-curlman-electron-windows-linux-design.md`

## Delivery Strategy

Keep the existing Electron application and close only the gaps that prevent dependable open-source Windows/Linux use. Work in small verified slices: audit current parity, harden desktop lifecycle, make packages predictable, add native-runner CI, document the actual installation paths, then validate the complete repository.

## Phase 1: Audit Existing Electron Behavior

1. Map the current renderer, preload, main-process, persistence, request, history, and shortcut behavior against the approved specification.
2. Identify incomplete native parity without widening into platform-specific redesign.
3. Add regression tests around any behavior changed by this implementation.

Verification:

- Existing Electron tests pass before changes.
- The implementation list contains no native-macOS-only work.

## Phase 2: Harden Cross-Platform Desktop Lifecycle

1. Ensure tray creation cannot make the app fail to launch when a Linux desktop does not expose tray support.
2. Provide application-menu commands for opening Curlman, starting a request, opening History or Settings, and quitting.
3. Keep the main window reachable when tray creation or global shortcut registration fails.
4. Preserve platform shortcut defaults and last-working-shortcut conflict behavior.
5. Keep compact sizing independent of expanded window dimensions.

Verification:

- Lifecycle helpers have deterministic unit coverage where practical.
- Main-process startup has a safe fallback path.
- The packaged app always has an explicit quit route.

## Phase 3: Make Windows and Linux Packages Predictable

1. Configure Electron Forge metadata, icons, categories, executable names, and artifact makers explicitly.
2. Produce Windows Squirrel output plus Linux DEB and RPM output for x64.
3. Add package metadata required by Linux makers.
4. Extend the package verifier to validate each operating system's output and required runtime resources.
5. Add scripts for package-only and installer-making workflows.

Verification:

- macOS package verification continues to pass locally.
- Windows and Linux maker configuration type-checks.
- CI verifies generated package contents and installer presence.

## Phase 4: Add Native-Runner CI and Release Artifacts

1. Run lint, type checking, tests, packaging, and verification on Windows and Ubuntu runners.
2. Upload clearly named Windows and Linux artifacts independently.
3. Generate SHA-256 checksums for public release files.
4. Keep Electron packaging independent from Apple signing secrets.
5. Prevent one failed platform from hiding the other platform's result.

Verification:

- Workflow syntax is valid.
- Windows and Linux jobs use their native shells safely.
- Release artifact paths match actual Forge output.

## Phase 5: Document the Open-Source Installation Experience

1. Put Windows and Linux installation steps beside native macOS instructions.
2. Preserve `npm install && npm run dev` as the contributor path.
3. Explain unsigned Windows warnings and Linux tray/global-shortcut limitations without suggesting bypasses.
4. Document package formats, supported x64 architecture, local data behavior, and uninstall paths.
5. Remove outdated statements that Electron installers are unavailable.

Verification:

- Every documented command exists in `package.json`.
- Every documented artifact is produced by Forge or CI.
- README keeps native Swift as the recommended macOS edition.

## Phase 6: Final Validation

1. Run `npm run typecheck`, `npm run lint`, and `npm test`.
2. Run `npm run package:electron` on the local macOS host as a packaging regression check.
3. Run `swift test` to ensure shared repository changes do not break native Curlman.
4. Run `git diff --check` and inspect the final diff for unrelated changes.
5. Push the implementation so Windows and Linux CI provide the authoritative native-platform validation.

Completion criteria:

- Source startup remains `npm install && npm run dev`.
- Windows and Linux installers are generated by native CI runners.
- Tray or shortcut limitations cannot trap the user in an unopenable or unquittable app.
- Documentation matches real commands and artifacts.
- Electron and Swift checks pass, with Windows/Linux CI green before release publication.
